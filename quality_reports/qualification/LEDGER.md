> **Disclosed residual on `git-guardrails.py`'s clean-tree check (r8, narrowed at r9).** The
> check no longer PREDICTS anything, so the residual is a list of forms it cannot SEE, not a
> list of semantics it might mis-model.
>
> **What it guarantees — this much, and no more (rewritten at r13).** For a history op the
> parser IDENTIFIES, the op must first be a STANDALONE SIMPLE COMMAND or it is denied outright;
> then, if it carries no escape token, the verdict is a LIVE `git status --porcelain` reading
> taken at hook time in the directory the invocation names. Nothing in the command text
> substitutes for that reading, so the ALLOW side is reachable only by a tree that is actually
> clean — or by the op never being identified at all. **Before r13 the first clause did not
> exist, and the guarantee was therefore only “the parser-selected repository was clean when
> the Bash tool call was authorized”** — materially narrower than the “starts from a
> clean tree” that the docstring summary and law 20 asserted. The standalone rule is what
> makes the reading mean anything, because it removes every command shape that could act
> between the reading and the op.
>
> **What it does NOT guarantee, stated because r9 falsified the previous wording:** that it
> identifies every shell form. It does not, and no version of it will. Identification is a
> best-effort textual parse of the command line, and it is the whole of what stands between an
> op and the reading. Where the parse can go either way the code is written to fall toward
> finding an op — an unknown git global option is consumed rather than mistaken for the
> subcommand, a `git` word later in a segment is still searched for, an unreadable `-C`
> directory degrades to reading the event cwd — but "falls toward deny where the parse permits"
> is not "denies everything it should". **A form the parser does not identify is not denied; it
> is invisible, and the op runs.** Those forms are listed below, and the list is a report of
> where the parser has been probed, not a proof of where it is complete.
>
> What it does NOT see: a history op carried by an interpreter (`python3 -c
> '...subprocess.run(["git","merge"])...'`); one inside a shell-wrapper payload (`bash -c 'git
> merge main'`, `env -S 'git pull'` — unlike `root-of-trust-guard.py`, this check does not unwrap
> `-c` payloads; more generally, an op that survives quoting as a single WORD is one word to the
> tokenizer); one run from an alias, a script file, a Makefile target, or a git hook; a
> `cd <other repo>` earlier on the same command line, since repository identity comes from
> `-C`/cwd only — **CLOSED at r13, no longer residual: a `cd` on a history op's command line
> now denies under rule 0, as do all the other multi-segment and selector forms**; any dirtying
> by ANOTHER PROCESS between the hook's decision and the command actually running (rule 0 closes
> the case where the SAME command line does the dirtying; it cannot close a concurrent writer,
> and ordinary accidents rather than concurrency are the threat model); and — the entry that
> matters most — **any shell
> form that puts the op somewhere this parser does not look.** Round 9 found five such forms that
> eight earlier rounds had not — compound-command keywords in front of the op, an exempt token

> three of them. The r8 replacement — "within the forms above, the decision is a live
> `git status --porcelain` reading, and **no textual feature of the command can make a dirty tree
> read as clean**" — is withdrawn at r9. Its first clause is true and kept. Its second clause was
> read as a guarantee about the whole check, and r9 falsified that reading by executing five
> classes of command text that made the guard never take the reading at all. The correct
> statement is the two paragraphs above: the reading cannot be faked, the parse can be missed,
> and where the parse is missed the residual is disclosed rather than denied.

> **Why the guards were qualified and the other five hooks were not.** These three *decide*: they
> return an allow/deny or a claim-staleness report that changes what happens next, so a dead one
> is a false green. The remaining five only nudge — a missed reminder, not a wrong verdict. They
> are listed as visible debt above rather than quietly omitted, because the failure this whole
> ledger exists to prevent is a checker nobody knows is unmeasured.

## Notes

- A **PASS at one difficulty is not a PASS at another.** Record the threshold.
- **Re-qualify after changing a checker.** A modified gate is unqualified.
- A **bad seed** (one the artifact already permits) produces a correct "pass" and looks like a
  broken gate. Verify the seed creates a real violation before recording a FAIL.

> **A qualification run found a real blind spot (2026-08-21).** Seeding "This template has 99
> skills." into `README.md` left every gate **green** — the count patterns are deliberately
> compound (they require several categories on one line) to avoid false-positives on prose like
> "start with 2-3 skills", and a bare count carrying only a template verb slipped between them.
> Fixed by adding template-verb patterns, then re-qualified **in both directions**: 3/3 seeded
> drifts caught, 0/3 false alarms on legitimate prose. **This is the whole argument for rung 0 —
> the gate had been green and wrong, and only a seeded defect could tell the difference.**

> **A rewrite silently removed a surface from coverage (2026-08-21).** Rebuilding
> `docs/index.html` around persona paths replaced its compound count phrasing with separate
> bulleted lines. Every gate stayed green — because the page was no longer being *checked*.
> Seeding a wrong count into the page proved it: exit 0, uncovered. Fixed by restoring one
> compound assertion line, then re-proved: seeded drift now caught.
>
> **The lesson generalises beyond counts.** Improving a surface can remove it from gate
> coverage without any gate going red, because a gate that matches nothing reports nothing.
> After editing any checked surface, seed a defect into *that surface* and confirm it is still
> seen. Total assertions went 29 → 34 across this release; a falling number is the signal to
> look for.
